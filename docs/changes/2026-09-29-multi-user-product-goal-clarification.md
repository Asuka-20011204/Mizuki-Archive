# 多用户产品目标与高可用边界更正

- 日期：2026-09-29
- 类型：产品与架构文档更正
- 状态：已完成文档更新，未改动业务代码

## 目的

明确“个人数字信息管理”的准确含义：个人描述每个用户管理自己资料的场景，不表示系统只能由作者本人使用。Mizuki Archive 的目标是服务多个相互隔离的用户，并以高并发、高可用作为持续建设的工程目标。

## 本轮范围

- 更新 `AGENTS.md` 的协作约束，禁止把个人场景误读成单用户系统。
- 更新 `README.md`、`docs/product.md`、`docs/architecture.md`、`docs/roadmap.md` 和 `docs/security.md` 的产品、架构、路线和安全表述。
- 明确每个用户拥有独立的资料、任务、派生产物、会话和缓存空间，默认禁止跨账号读取。
- 明确当前测试只能证明已完成的多用户隔离和共享状态基础，不能直接证明生产级容量或可用性。

## 设计取舍

1. **多用户优先于单用户假设**：数据模型、服务端授权、缓存命名空间和任务归属必须从多个用户的越权风险出发设计。
2. **单体不等于单用户**：当前继续保持 Go 单体 API + 独立 Worker 的可读边界，通过共享 MySQL、Redis、RabbitMQ 和后续共享文件/对象存储支持横向扩展。
3. **目标与证据分开**：高并发、高可用是项目目标，但只有完成对应环境、负载和故障切换测试后，才能记录具体容量、延迟和可用性结论。
4. **暂不开放跨账号协作**：多个用户可以使用系统，但默认只能访问自己的资料；共享、协作和组织级权限另行设计，不通过放宽当前权限过滤实现。

## 当前验证结果

- 已有多用户身份、资源、任务、派生产物、会话和 Redis 最近访问命名空间的归属隔离基础。
- 已有两个模拟 API 实例共享 MySQL 会话和资料归属状态的验证。
- 已有本机 Docker 隔离部署、Redis/RabbitMQ 故障回退、备份恢复和固定合成负载记录。
- 上述结果不等于已完成真实多进程、多节点高可用；多 API、多 Worker、数据库/缓存/Broker 集群、共享存储、TLS 入口和持续混合负载仍需单独验收。

## 遗留风险与下一步

- 需要使用真实 SMTP 完成多账号浏览器注册、登录、退出和资料隔离闭环。
- 需要启动真实多 API 进程和多个 Worker，验证跨进程会话、任务恢复和故障切换。
- 需要在 PDF、图片、TXT/Markdown 混合负载与多用户并发下形成可复现容量基线。
- 需要在生产部署前补齐 TLS、入口限流、密钥托管、镜像扫描、数据库高可用和共享文件/对象存储方案。
