# 2026-09-29 · V5 并发控制与背压

## 目的与范围

个人资料的手动文本提取和缩略图处理可能同时提交。V5 在保留 V2 数据库模式和 V3 RabbitMQ 模式的前提下，为任务创建添加全局积压上限，并限制单进程实际执行并发。

## 取舍

- `PROCESSING_WORKERS` 默认 2，范围 1–4；数据库模式运行固定 Worker Pool，RabbitMQ 模式以 prefetch 控制并发。进程数增多时总执行槽位也会增多，部署必须单独核算。
- 迁移 `006_processing_capacity.sql` 初始化唯一锁行。事务先锁该行、确认资料存在及幂等任务，再统计 `pending + processing`；未超限才写任务和可选 Outbox。满额时 API 返回 `429 queue_full` 并提示 5 秒后重试。默认上限 100，仅限制任务积压，不限制资料库空间。
- 任务执行租约与最多三次尝试沿用 V2/V3；Worker 取消后仍需妥善释放资源。RabbitMQ 断线只重新连接，不跳过 MySQL 中的业务任务状态。
- 没有先引入 Redis 信号量或多租户配额，因为个人系统的持久容量和失败恢复仍以 MySQL 为准。

> 术语更正：这里的“个人系统”指个人资料管理场景，不表示系统只有一个用户；当前容量门禁是全局处理资源保护，用户级配额仍需结合多用户容量模型单独设计。

## 验证

- `go test ./...` 与 `go vet ./...`：通过；`npm run build`（含 `vue-tsc`）：通过。
- 独立 `mizuki_test_v5_` 前缀 MySQL 8.4 临时库：5 个并发创建请求中 2 个成功、3 个拒绝；失败后释放容量重新提交，RabbitMQ 模式 Outbox 数与任务数相符；Worker 重启后接管过期租约。测试完成后删除该隔离库，正式资料未参与。
- Controller 测试覆盖满额时 HTTP 429、稳定错误码和 `Retry-After`；RabbitMQ 消费有界并发及取消后关闭行为由队列测试覆盖。

## 遗留风险与下一步

- 尚未在固定数据集上量化并发槽位选择、积压曲线、内存峰值和重启恢复时间；V7 用同环境基线/优化对比，不能把默认值说成最佳值。
- V6 增加可重复部署与备份恢复演练；部署时避免多个不同投递模式的 Worker 同时消费，API 与 Worker 必须共享受控文件目录和 MySQL。
