# V12 生产数据库权限分离

## 目的

将数据库结构变更与 API/Worker 运行时分开，避免常驻业务进程使用拥有 DDL 权限的账号。此轮对应路线图中 V6 第 61 行的第一项，不把单机 Docker 演练写成完整生产环境。

## 范围

- 新增 `cmd/migrate`，使用 `MIGRATION_DSN` 执行版本化 SQL、管理员初始化和旧数据归属回填。
- `compose.deploy.yaml` 新增 `db-access-bootstrap` 和一次性 `migrate` 服务。
- API/Worker 支持 `APP_AUTO_MIGRATE=false`；生产运行账号只执行业务读写。
- Docker 镜像同时构建 API、Worker 和迁移程序。
- 同步部署、架构、目录、安全、README 和路线图文档。

## 设计取舍

- 本地开发仍默认允许 API/Worker 自动迁移，减少首次启动摩擦；生产编排显式关闭，避免把开发便利带入生产。
- 迁移账号当前拥有目标数据库的全部权限，因为版本化迁移需要创建表、索引、约束并执行兼容回填；该账号只由一次性容器使用，不作为常驻应用账号。
- API/Worker 运行账号只保留 `SELECT`、`INSERT`、`UPDATE`、`DELETE`。这能阻止运行时 DDL，但不能替代 MySQL 网络隔离、TLS、密钥托管、备份和审计。
- 管理员密码哈希只注入迁移服务；API 在生产启动时从已存在的用户记录读取哈希，不再要求运行环境提供管理员哈希。

## 评审修正

- 评审发现已有管理员不会应用新的 `APP_ADMIN_PASSWORD_HASH`，导致密码轮换配置静默失效；现已在迁移入口执行 bcrypt 格式校验，并在哈希变化时更新已有管理员记录。
- 校验发生在迁移入口执行数据库迁移之前；`EnsureAdminUser` 同时保留防御性校验，避免其他调用方绕过入口写入无效哈希。

## 遗留风险

- TLS 入口、网关限流、密钥托管和镜像漏洞扫描尚未完成。
- 迁移账号仍拥有目标数据库的较宽 DDL 权限，需接入正式密钥管理、审批和审计后再用于生产。
- MySQL、Redis、RabbitMQ、文件存储和入口层的跨节点高可用尚未验收。
