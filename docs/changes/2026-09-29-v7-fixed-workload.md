# 2026-09-29 · V7 固定负载与 Worker 轮询优化

## 场景与可重复步骤

目标是解释个人资料库在小型批量文本处理与认证列表读取下的实际行为，不以一次微基准声称生产吞吐。测试机为 Windows/amd64、Intel i5-12450H（8 核、12 逻辑处理器）、31.8 GiB 内存；Go 1.25.3，Docker Engine 29.2.1，容器 MySQL 8.4.11。每次创建全新 `mizuki_test_v7_` 前缀空库，迁移 `001`–`006` 在计时前完成；测试结束删除隔离库。真实资料库与用户文件未参与。

- 任务负载：24 条固定 128 KiB 合成纯文本，先全部提交为 `pending` 再启动数据库模式 Worker；从池启动到 24 条全部成功为计时范围。单/双 Worker 都用生产的 1 秒**空闲**轮询配置；完成数每 50 毫秒查询一次。排除迁移、造数和客户端上传时间，包含实际 MySQL 领取、文件读取、派生写入与索引提交。记录 Go 进程抽样堆峰值与增量分配，不等同容器 RSS/CPU 峰值。
- HTTP 负载：另外的空库建立 24 条合成元数据，由 `httptest` HTTP 服务签发会话 Cookie；10 个客户端并发读取 100 次私有资料列表，输出成功数、总耗时、请求延迟 p50/p95。此测试不经过前端、Nginx、TLS 或上传路径。
- 复现：在空的独立测试库设置 `MIZUKI_TEST_MYSQL_DSN`（库名必须以 `mizuki_test_v7_` 开头）和 `MIZUKI_RUN_BENCHMARK=1`，运行 `go test ./internal/service -run '^TestV7ProcessingWorkload$' -count=3 -timeout 3m -v`，以及 `go test ./internal/controller -run '^TestV7AuthenticatedListWorkload$' -count=3 -timeout 90s -v`。**分开运行**，不要让两组测试共享库并行；退出后清理该独立库。未显式设置开关时测试自动跳过。

## 解释、成本与限制

- 瓶颈是 Worker 每完成一个任务都无条件休眠 1 秒；单 Worker 在 24 条任务中累计多次空等。现在**只有没有可领取任务时**才休眠，数据库故障仍立即返回，且新增回归测试防止再次出现满积压休眠。
- 三轮优化后单 Worker 排空中位数 1.707 s，双 Worker 为 1.953 s；这个轻文本样本中双槽位并未稳定提高吞吐。保留默认 2 是兼顾未来混合 PDF/图片的保守值，不能据此扩大 Worker 实例数。每个槽位在满积压时更频繁访问 MySQL；空闲仍按 1 秒轮询，因此瞬时数据库连接和 CPU 开销可能增加。
- 24 个 128 KiB 文本任务仅约 3 MiB 原件，抽样 Go 堆最高约 3.5 MiB，不能覆盖 50 MiB PDF、4000 万像素图片、外部 MQ、持续流量或跨主机恢复。HTTP 测试只计成功响应，不包括用户浏览器渲染、文件下载和 TLS 网关。测试可能受本机后台负载影响，三轮差异已如实保留。
- 异常恢复与幂等仍依赖 V5 隔离 MySQL 与 V3 Broker 测试；本轮未重新模拟进程崩溃，不以吞吐数据替代可恢复性证明。上线前对目标硬件补充长时间混合负载、RSS/CPU、数据库连接数和备份窗口，再决定并发度与容量上限。
