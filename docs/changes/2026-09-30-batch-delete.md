# 混合来源批量删除与持久文件清理

- 日期：2026-09-30
- 目的：完成 P0 批量操作中的危险删除，同时避免跨账号或进程中断造成半批数据损坏和孤儿文件失控。

## 范围与取舍

- `POST /api/batch/delete` 只接受当前用户 1–50 个不同 `{source,id}` 与明确 `confirm: "DELETE"`；8 KiB 请求上限、完整 JSON、逐账号限流、缺失/越权整批拒绝。
- 数据库事务中软删除文件及其标签，清除对应任务、派生正文与 outbox，硬删除站外卡片及其标签，留下 `017` 迁移建立的文件清理账本。事务失败不碰文件；事务成功后清理原件与派生文件，失败数量返回 `cleanup_pending`，后台定期重试。
- 收件箱和归档区在用户输入“删除 N”后提交，成功/待清理/错误都有明确反馈；不可撤销，不把归档伪装为回收站。具体设计见 [ADR 0011](../decisions/0011-batch-delete-cleanup.md)。

## 验证

- 服务与 HTTP 测试覆盖匿名、非法/重复/越权选择、确认字段、尾随内容、大小、删除数量以及清理失败重试。独立 `mizuki_test_` MySQL 8.4 库中，仓储全量测试通过；新增实库用例验证失败项延迟后不阻塞后续清理，迁移重复执行通过。`go vet ./...`、无实库 DSN 的 `go test ./... -count=1`、前端 11 项测试、TypeScript 检查与构建、`git diff --check` 通过。
- 同一隔离库复跑或全量跨包复用时，现有 `TestMySQLFinalizeOwnershipBackfillsLegacyRows` 因新库迁移后 `user_id NOT NULL` 无法插入旧版空归属夹具而失败；这是遗留回填用例与当前迁移终态的冲突，未将失败算作通过。浏览器手动交互尚未验收，不能宣称已经上线。

## 风险与下一步

- 清理账本和物理文件删除之间有短暂窗口；多节点必须共享相同受控文件存储，不能仅靠 Redis 缓存宣称已删除。备份保留期、历史单项删除产生的派生产物残留仍需独立治理。
- 已整理资料的批量选择入口、删除交互的真实浏览器验收，以及高并发/高可用的混合负载仍是路线图未完成项。
