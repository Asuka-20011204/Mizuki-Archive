# 开发与 Git 规范

## Git 初始化与提交

- 仓库初始化后使用 `main` 作为主线；不直接向主线提交未经验证的功能。功能分支示例：`feat/resource-upload`、`fix/file-cleanup`、`docs/product-scope`。
- 提交遵循 Conventional Commits 的类型，**描述与正文用中文**：`feat: 实现资料上传校验`、`fix: 修复删除后残留文件`、`docs: 明确资料库范围`。常用类型：`feat`、`fix`、`docs`、`test`、`refactor`、`perf`、`chore`、`ci`。
- 一次提交聚焦一个逻辑目的；不要夹带个人文件、生成数据或无关格式化。检查 `git status` 和 `git diff --check`，逐项审查暂存内容，尤其是文件名与二进制文件。`.gitignore` 不是防泄露措施，已被追踪的敏感文件仍须人工处理并轮换泄露凭据。
- PR/合并说明包含目的、变更、风险、测试结果、回滚方式；以目标分支到 HEAD 的**完整差异**评审。用户已要求较大修改验证后提交中文信息；未获明确要求不推送、不创建远端。

## 一项功能的流程

1. 在 `docs/product.md` 和 `docs/roadmap.md` 找到用户场景与验收条件；不清楚的行为先形成可检验假设。
2. 写最小设计：状态、权限、存储一致性、失败恢复、性能预期；重大取舍补一条 ADR。
3. 先写失败案例/测试，再实现最小垂直切片，必要时做重构；不要先铺满架构抽象。
4. 本地跑对应测试，再跑格式化、静态检查、集成与关键流程测试；覆盖率目标 80%，同时看断言和边界，不伪造通过结果。
5. 评审差异；认证、上传、文件、SQL、缓存、MQ 变更额外走 `docs/security.md`；修复高危问题后再合并。
6. 同步 README 的真实运行命令、环境变量名称、迁移与备份步骤；较大修改在检查暂存差异与敏感信息后提交，并向用户报告提交哈希。推送与合并仍由用户决定。

## 用时与质量的执行策略

1. **先规划关键路径并控制耗时**：从路线图定位可验收成果，列出依赖、数据/权限风险、要修改的文件和必要验证，预估本轮实现与验收耗时；不先穷举整个项目。初步定位通常约 3 分钟内完成，约 10 分钟内产生首次代码、测试、文档或关键证据；未做到就说明原因并换更直接的路径，不继续空转。
2. **合理分工**：互不依赖且写入范围不重叠的实现、文档或审阅可以并行；依赖上一结果的工作留在关键路径上直接处理。并行测试应各用独立库、端口和夹具；没有可安全并行的任务时不增加协调成本。
3. **分层验证**：变更后先跑相关单测和定向检查，失败就地修复；接近交付时再跑全量测试、构建、安全审查与需要的真实交互。实库测试每轮使用新的 `mizuki_test_` 隔离库，避免跨包并发迁移和复用夹具污染结论；必要时串行或分别建库。记录实际命令与失败，不把窄范围通过描述为全面验收。
4. **管理长任务**：执行容器、浏览器或耗时测试前确认环境/运行句柄，不重复启动已经运行的进程；等待超时只重新观察同一任务，不把超时当失败。进展更新只在切片完成、风险变化或进入长时间验证时发送，说明具体结果与下一步。
5. **及时收口**：安全与数据一致性门禁不能省；非阻塞的未来优化进入路线图。接近预计耗时仍无法完成时主动交代剩余任务、风险和调整方案，不用无限研究代替交付；当前切片通过可执行验收后同步文档、评审完整差异并按提交规则交付。对未验收的浏览器流程、供应链扫描或性能指标明确保留未完成状态，不缩减路线图总体目标。

## 代码与环境约定

- 新代码按 `internal/model`、`internal/controller`、`internal/service`、`internal/repository` 与 `web/src` 落位；请求验证留在 Controller，业务校验与状态迁移留在 Service，GORM 持久化留在 Repository。跨层调用只向内，不从 Service 引用 Gin 或 Vue。
- Go 使用 `gofmt`、`go vet`、`go test ./...`；前端使用仓库实际选择的包管理器与脚本，不凭空宣称已有 lint/build 命令。
- 配置只通过环境变量/密钥管理注入，提供**不含实际凭据**的 `.env.example`；启动时验证必需项。开发、测试、生产使用不同数据与凭据。
- 数据库结构通过版本化迁移；改动表结构同时考虑回滚/数据兼容，迁移前备份。
- CI 最低门槛计划：格式/静态检查、后端/前端测试、构建、依赖与密钥扫描；引入服务后加数据库和队列的集成测试。CI 配置建立后才标注具体命令。
- 本机/生产不能使用真实个人资料作为公开示例或上传测试夹具；演示资料须可公开且授权明确。

## 中文注释规则

- 所有具名函数、方法、前端 API 箭头函数及测试辅助函数，在定义正上方写中文注释：它解决什么问题，必要时说明输入、返回值或副作用；导出函数以函数名开头，便于 Go 文档工具索引。
- 匿名回调在紧邻的调用处说明目的；如果涉及异步、权限、清理或状态竞争，再说明触发时机和失败/取消行为。简单比较回调由所在表达式的注释覆盖，不为每个参数机械写一行。
- 安全校验、文件与数据库不共享事务、缓存/任务边界等复杂设计，注释应解释**为什么这样做**、仍有什么限制。文档承载全局架构；代码注释保留阅读当前函数必需的上下文。
- 不写 `// 设置变量`、`// 返回结果` 之类的逐行翻译；变更行为时同步更新失效的注释和测试。评审时检查“注释描述的事实”与实际代码是否一致。

## 每轮重大变更留痕

在 `docs/changes/YYYY-MM-DD-主题.md` 创建记录；同一天多个独立变更用不同主题文件。每条至少写：目标和用户影响、变更范围、主要决策与替代方案、验证命令及真实结果、已知限制/风险、下一步。涉及架构决策另写 `docs/decisions/` ADR，避免把进度日志当作决策记录。变更记录随本轮文件一同评审和提交，修复结果继续追加而不是删除失败历史。
