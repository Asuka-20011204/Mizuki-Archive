# 技术方案（V1 分层设计）

## 原则与候选技术

- **业务先于技术**：产品是多用户、各自私有资料空间；先完成账号/归属隔离，再对真实的耗时处理、热点读取和任务突发分别使用 Worker、RabbitMQ、Redis。
- **确定技术栈**：Go + Gin + GORM + MySQL；文件初期存放于服务端受控目录。前端 Vue 3 + TypeScript。选择轻量单体而不是微服务，API 与未来 Worker 可共享领域包但独立进程。
- **可替换边界**：文件存储、任务投递、元数据持久化、缓存都通过清晰接口隔离；不为尚未出现的提供方预先实现复杂抽象。

验证码邮件的 SMTP 传输适配器位于 `internal/notification`，强制 TLS。用户、会话、资料、任务、派生产物和缓存必须以 `user_id` 为服务端边界；前端不得提交或决定所有者。旧单管理员数据迁移到首个用户后，才开放邮箱注册/登录。身份演进见 [ADR 0007](decisions/0007-verified-identity-boundary.md)。大陆手机号认证使用独立身份/挑战表和 `PhoneSender` 端口；尚无供应商适配器，`cmd/server` 不注入服务，详见 [ADR 0008](decisions/0008-mainland-phone-foundation.md)。

## 多用户、高并发与高可用目标

“个人数字信息管理”描述的是资料管理领域和每个用户的使用场景，不等于单用户部署。系统必须允许多个相互隔离的用户注册使用：每个用户拥有自己的资料、任务、派生物、会话和缓存命名空间，默认不开放跨账号共享。用户数量增加时，权限边界不能依赖前端约定，性能优化也不能牺牲隔离性。

高并发、高可用是本项目的明确工程目标；当前采用“先建立可扩展边界，再用实测逐步提升可靠性”的方式演进：

- API 进程保持无状态，使用共享 MySQL 会话、Redis 限流/热点缓存和外部文件存储，支持多个 API 实例水平扩展；独立部署的 Web 代理按 Docker 服务 DNS 重新解析 API 副本，读请求可在副本故障时切换。
- 耗时处理通过 RabbitMQ + 多 Worker 解耦，使用持久任务、Outbox、租约、幂等和有限重试，避免请求线程被文件处理拖住。
- MySQL、Redis、RabbitMQ、文件存储和入口网关分别设计健康检查、故障转移、备份与恢复，不把单机 Docker 演练写成高可用承诺。

当前已验证的是本机隔离部署、固定负载、有限 Worker 并发、Redis/RabbitMQ 故障回退、备份恢复、两个模拟 API 实例共享 MySQL 会话和用户归属状态，以及隔离 Compose 项目中 2 个 API/2 个 Worker 的单副本 API 停止演练；这说明系统已经按多用户和可扩展方向建立基础，但不等于完成生产级高并发高可用。跨进程 API、多副本 Worker、MySQL 主从/故障切换、Redis Sentinel/Cluster、RabbitMQ 集群、对象存储和真实持续压测尚未验收。任何吞吐、延迟和可用性数字都必须绑定测试环境与负载说明。

## 逻辑视图

```text
Vue View（资料库 / 搜索 / 详情 / 任务中心）
             │ HTTP
             ▼
Gin Router / Controller（鉴权、输入输出、HTTP 状态）
             │
             ▼
Service（上传、查询、文件校验、业务规则）
             │
             ├── Repository ── MySQL（用户、资料、会话、后续任务元数据，所有私有查询带 user_id）
             └── File Storage ── 本地受控目录

V2：Go Worker ← 持久任务记录
V3：Go API → MySQL processing_jobs + processing_outbox（同一事务）→ RabbitMQ → Go Worker
V4：Go API ↔ Redis（标签/任务短缓存、最近访问 ID、共享限流）
V6：本机 Docker Web(Nginx) → API + Worker → MySQL + 共用数据卷
V14（可选覆盖）：TLS Web(Nginx) → API + Worker；证书由宿主机或外部密钥系统只读挂载，不复制进镜像。
```

V1 不依赖消息队列或缓存；V2 可先用数据库持久任务与受控 Worker 验证处理能力。V3 接入 MQ 时不能假设“写数据库 + 发消息”天然原子化：采用事务性 outbox 或等效方案，发布确认后再标记已投递；消费至少一次，处理结果必须幂等。

## MVC 在本项目中的落点

| 层 | 位置 | 允许做什么 | 不做什么 |
| --- | --- | --- | --- |
| View | `web/src/` | 页面、交互、展示、无状态 API 调用 | 在浏览器决定权限或直接连接数据库。 |
| Controller | `internal/controller/` | Gin 路由、会话中间件、参数解析、HTTP 状态和响应 | 操作 SQL 或直接拼文件路径。 |
| Service | `internal/service/` | 上传校验、资料流程、事务边界与错误映射 | 感知 Gin 或把 HTTP 请求对象传给仓储。 |
| Model | `internal/model/` | 资料、筛选、会话等领域数据 | 持有数据库连接或 Web 状态。 |
| Repository | `internal/repository/` | 使用 GORM 操作 MySQL，保持参数化查询；接口供 Service 测试替换 | 决定 HTTP 响应和页面布局。 |
| Composition | `cmd/server/` | 加载配置、创建连接、接线、启动与关闭 | 放置业务规则。 |

这是适合 Go API + Vue SPA 的务实 MVC：Service/Repository 是辅助分层，不把 MVC 误用为所有目录必须叫 `models/views/controllers`。接口由使用方按需要定义，避免为单个实现层层空壳包装。

当前入口、文件级职责和上传/登录调用路径见 [项目目录导览](project-structure.md)。

数据库迁移使用内嵌的版本化 SQL（当前 `001` 至 `019_resource_relations.sql`），由 `schema_migrations` 记录已应用版本；不使用 GORM AutoMigrate 修改生产表结构。`005` 回填尚未投递的旧任务，`006` 建立全局容量锁行，`007`/`008` 建立用户和验证码表，`009` 在迁移锁内兼容检查并补建归属列与用户范围索引；`010` 建立独立的外部资源卡片与标签关联表；`011` 在锁内按需补建两表的整理状态列和用户索引；`012` 为大陆手机号认证增加可重试的身份列/唯一索引及挑战表；`015` 补建外部卡片收藏列；`016` 补建两类资料的归档时间列和用户索引；`017` 建立持久文件清理账本；`018` 建立每文件最多 100 条的私人笔记表；`019` 为同账号两类资料建立无方向关联，并在删除资料时清理。正式执行前先备份数据库。

私人笔记属于上传文件而非外部资源卡片；Repository 以会话用户和未删除文件双重限制读写，创建时锁文件行控制数量，Service 校验文字和仅 PDF 可填的页码。统一搜索只返回匹配的文件元数据，以文件范围 `EXISTS` 查询笔记正文、摘录和来源；详情按会话读取完整笔记。单项和批量删除文件的事务会同时清理在线笔记行；已生成的备份仍按独立保留策略处理。详见 [ADR 0012](decisions/0012-private-resource-notes.md)。

`GET /api/export` 在会话下生成同账号的版本化 JSON：Repository 使用 MySQL 只读 REPEATABLE READ 快照，按固定顺序读取未删除文件、卡片、标签、笔记和两端可见的关联；Service 限制结果至 32 MiB，Controller 限制频率和同时导出数，并在完整生成后才写附件响应。超过每类行数或响应大小上限时返回明确错误，不输出部分 JSON；原件与派生产物既不从受控目录读取，也不访问外部卡片地址。格式与边界见 [ADR 0013](decisions/0013-portable-metadata-export.md)。

外部资源不进入上传文件表，不触发处理队列，也不把卡片位置映射为服务端文件路径。`external_resources.user_id` 来自经验证的服务端会话；Get/List/Update/Delete 都在仓储层强制限定归属，缺失身份直接拒绝。标签与卡片在同一 GORM 事务创建或替换；状态仅由用户手动维护，服务端不访问链接。

收件箱使用独立 `InboxStore`/Service/Controller；按会话归属分别查询待整理且未删除的站内文件、待整理的外部卡片，每来源每页最多 50 条。`organization_status` 独立于外部链接 `status`，`PATCH /api/inbox/:source/:id` 只修改前者；重复设置相同目标可安全重试，跨用户返回与不存在一致的 404。迁移默认历史资料待整理，需在升级前预估旧库条目数量；此操作不会更改原件或任务。

`PATCH /api/inbox/batch` 接收至多 50 个 `{source,id}` 和明确的 `pending`/`organized` 目标状态。Service 拒绝重复和非法 ID；Repository 在一个 MySQL 事务内对文件和外部卡片分别锁定当前用户的所有行，缺失或越权即整批回滚，再更新状态。响应的 `count` 表示受理的选择数量而非实际变化的行数；UI 仅在成功后提供一次显式恢复到 `pending` 的撤销按钮。

`PATCH /api/batch/tags` 同样仅接受已登录用户至多 50 项不同的 `{source,id}`，`tag` 经统一规范化，`mode` 限于 `add`/`remove`。仓储先按固定顺序锁定混合来源的全部本人条目，再在同一 MySQL 事务内修改文件关联表或卡片标签表；单文件替换标签也锁定文件主行。某项缺失/越权/软删除或达到 10 标签上限时整批失败。返回 `changed` 和其 `count`（真正发生变化的条目），重复增删返回空变化集。前端目前仅从待整理收件箱选择，标签“反向恢复”不是版本化撤销，其他设备若在此后编辑同一标签可能被覆盖；请求成功但响应丢失后的重试也不能恢复首次变化项，若需可靠撤销应增加操作 ID、持久结果及版本冲突检测。批量删除仍需单独设计。

`015` 在迁移锁内为外部卡片加默认 `false` 的收藏列；准备函数检查已存在列的定义并允许 DDL 已执行但记录未写入时重试。`PATCH /api/batch/favorites` 要求明确的布尔目标，先在同一事务锁定全部文件和卡片的本人行，再只更新实际不同的收藏状态。编辑卡片不写收藏列，避免旧表单覆盖并发收藏。返回 `changed/count` 供一次反向操作；并发更改或响应丢失后重试不具备真正的版本化撤销。入口目前是待整理收件箱和单张外部卡片，尚未覆盖已整理文件的批量选择。

`016` 为文件及外部卡片增加可空 `archived_at`，按迁移锁逐表验证列和索引以便在 DDL 中断后继续。`PATCH /api/batch/archive` 只在私有会话中接受明确布尔目标和 1–50 个不同的 `{source,id}`；仓储事务先锁定并核验全部归属与文件软删除状态，再只修改实际状态不同的行。`GET /api/archive?page=` 分别分页返回当前用户的归档文件及卡片；活动列表、统一搜索、待整理收件箱与最近访问排除归档项，但归档不删除原件、标签或整理/链接状态。前端在收件箱确认归档、在归档区选择并确认恢复，返回真实变化数量；并发状态覆盖与响应丢失后的反向操作不是版本化撤销。已整理资料的批量归档入口与批量删除仍未实现。

`POST /api/batch/delete` 私有接口要求 1–50 个不同条目和显式 `confirm: "DELETE"`。仓储在一个事务中锁定、核验全部归属，软删除站内文件并解除标签，清除对应处理任务、派生正文与 outbox，硬删除站外卡片（绝不访问外部地址）；同时把原件和派生存储键写入 `017` 清理账本。提交后 Service 仅按服务端生成的 ID 清理受控目录；失败不回滚已提交的删除，而是返回 `cleanup_pending` 计数，API 后台每分钟重试。旧消息找不到任务后被幂等忽略；处理中任务若完成写入遇到已删除任务则清理临时产物。删除无法从页面撤销，备份仍可能保留旧内容；详见 [ADR 0011](decisions/0011-batch-delete-cleanup.md)。已整理资料的批量入口仍未完成。

生产编排通过 `db-access-bootstrap` 创建独立迁移账号，并把 API/Worker 的运行账号权限收窄为当前业务所需的 `SELECT`、`INSERT`、`UPDATE`、`DELETE`。一次性 `migrate` 容器使用 `MIGRATION_DSN` 执行 DDL、管理员初始化和旧数据归属回填；API/Worker 设置 `APP_AUTO_MIGRATE=false`，启动时只读取已存在的管理员身份。这样可以把“发布应用”和“修改数据库结构”分开审计与回滚，但仍需要后续补齐迁移前备份、TLS、入口限流和密钥托管。

V3 消息只含版本和任务 ID。事务 Outbox 的发布确认与后置 ACK 提供至少一次交付；MySQL 租约和成功状态负责幂等。发布通道断开重建连接，过期租约与丢失的已发布事件由定期修复补偿；隔离队列用于排查异常消息。任务最多执行三次（包括租约到期重领）；发布失败不直接标记业务任务失败。数据库模式可作为回滚开关，不能与 RabbitMQ Worker 同时消费同一任务。

V4 Redis 可丢失：标签和任务状态短时缓存，资源详情/文件下载及私有资料列表仍由 MySQL 校验，避免软删除后的旧列表重新写入缓存。最近访问只存 ID、上限 20 且 90 天到期，删除时尽力清理，查询时始终回源权限校验。共享固定窗口按网络地址限登录总请求 30 次/15 分钟，单进程继续按失败 5 次/15 分钟限制；Redis 故障退回本地保护，不宣称跨进程保障。真实吞吐增益留待 V7 基线对比。

V5 背压在 MySQL 中执行：新任务创建事务先锁 `processing_capacity` 的单行，再锁来源资料，优先识别同来源/类型/哈希的可复用任务，最后统计全局 `pending + processing`。超过 `PROCESSING_MAX_OUTSTANDING`（默认 100，允许 1–1000）时回滚并返回 429；任务与 RabbitMQ Outbox 事件必须同时提交。这个上限针对待处理任务数量，不是每个用户的存储配额，也不限制已经上传的原件。数据库 Worker Pool 每进程允许 1–4 个槽位（默认 2），RabbitMQ prefetch 限于槽位数；多进程部署时总并发数是各实例槽位之和，须在压测中重新评估。任务完成或失败释放容量，过期租约继续由 Worker 接管。

V6 本地 Docker 使用独立 Compose 项目隔离开发库。Web 在本机环回端口同源代理 API，API/Worker 不暴露宿主端口、共用原件/派生产物卷；数据库卷独立。`/healthz` 只看 HTTP 进程，`/readyz` 限时检查 MySQL。容器非 root 且只读根目录；V14 已提供可选 TLS 入口和 Docker Secrets 文件注入，镜像漏洞门禁仍需在安装 Trivy 的环境执行。参见 [部署与恢复](deployment.md)。

入口限流分为两层：Nginx 按 `$binary_remote_addr` 对认证入口和 API 入口做边缘限流，Gin/Redis 再按业务接口和用户输入做应用级限流。API 默认不信任转发头；只有独立部署中 API 不直接暴露且 Nginx 覆盖 `X-Real-IP` 时，才通过 `APP_TRUST_PROXY_HEADERS=true` 使用该地址。若代理链不是本项目可控的单层入口，必须保持关闭，否则客户端可伪造限流身份。TLS 覆盖还会传递 `X-Forwarded-Proto: https`，使 API 根据 `APP_ORIGIN=https://...` 设置安全 Cookie。

V7 固定文本任务负载发现数据库 Worker 即使有积压也每完成一条休眠 1 秒；现调整为领取到任务后连续处理，只有空队列才等待下一轮询间隔。固定 24 条文本任务的排空耗时、单双 Worker 差异和带鉴权列表读取的 p50/p95 见 [量化记录](changes/2026-09-29-v7-fixed-workload.md)。这不是 PDF/图片混合负载的容量承诺。

## 领域草模

重复提醒沿用 Model/Controller/Service/Repository 边界：Service 在成功保存后请求查重；Repository 用 `user_id` 与哈希/链接摘要索引定位另一条未删除文件或同账号外部卡片，Controller 只返回可见名称与 ID，Vue 仅展示提示。`013` 迁移在锁内可重试地补建用户范围索引和 `external_resources.location_key`，分批为旧卡片回填摘要。外部地址只做纯文本 URL 规范化，不发出网络请求；非 HTTP(S) 位置不参与查重。数据库查重异常不会撤销已成功的保存，响应会指出重复检查暂不可用；这是提醒而不是唯一约束或存储去重。

统一搜索提供受会话保护的 `GET /api/search?q=...&page=...`，Controller 只做 HTTP 校验，Service 限制关键词最多 100 字符、空关键词须有其他实质筛选条件、最多 1000 页和每类最多 20 项；Repository 强制 `user_id`，文件过滤软删除、按名称/标签/提取正文匹配，卡片按元数据/备注/标签匹配。两类查询均采用参数绑定和稳定的创建时间/ID 排序，结果以来源分组；任何一类失败不返回部分数据。当前部分匹配使用 `LOCATE` 与转义后的 `LIKE`，限制返回窗口但不能保证扫描成本随库规模恒定；大量数据或持续负载需先实测瓶颈，必要时评估分词、全文索引和专门搜索服务，不把它称为已完成的生产级全文搜索。

`014` 新增 `saved_search_views`：视图只保存组合筛选条件和用户归属，不缓存资料结果。`GET /api/search` 可附加 `source`、`kind`、`tag`、`organization_status`，Service 拒绝空条件并限制长度和状态值，Repository 在文件和卡片 SQL 查询前按归属、类型、标签、整理状态施加条件，保留各来源独立分页。`GET/POST/DELETE /api/search/views` 单独管理视图；Service 校验名称与随机 ID，Repository 锁住账号行在事务中限制每账号 30 个，并用唯一约束拒绝重名。视图应用时仍走实时搜索的权限与限流路径，不把保存动作当成资料授权。

| 实体 | 关键内容 | 约束 |
| --- | --- | --- |
| Resource | ID、展示名、原文件名、受控存储键、类型、字节大小、哈希、创建/更新时间、收藏状态 | 路径不接受客户端直接指定；哈希不等于去重业务决策。 |
| Tag / ResourceTag | 标签名称、资料关联 | 手动标签优先，自动分类暂不做。 |
| ProcessingJob（V2） | ID、资料 ID、任务类型、状态、尝试次数、错误摘要、创建/更新时间 | 只能操作有权限的资料；状态转移与重试有上限。 |
| DerivedAsset（V2） | 来源资料、产物类型、存储键、版本 | 可重新生成；不能覆盖原件。 |

状态候选：`pending → processing → succeeded / failed`。取消、重试与进度百分比需要明确语义和能力支持，不能从模拟进度冒充真实处理进度。

## 关键数据流与一致性

1. **上传**：请求身份校验 → 限制大小与格式 → 流式写入隔离的临时文件 → 计算哈希并验证实际类型 → 原子移动/受控提交 → 创建数据库记录 → 返回资源 ID。跨文件系统与数据库不是同一个事务；失败执行清理，另设孤儿文件巡检。不得用未经规范化的原始文件名拼接存储路径。
2. **查询**：始终按授权范围过滤；名称/标签/类型筛选与稳定分页先由数据库完成。确有搜索质量与规模需求再评估全文索引，避免把 `LIKE` 宣称为完整的全文搜索。
   **收藏**：`PATCH /api/resources/:id/favorite` 要求已认证同源请求和明确布尔值，只写入 `resources.favorite`；重复提交同一状态仍成功，缺失资料返回 404。文件原件不受影响，不采用非幂等的“反转”指令。
3. **整理与删除**：名称编辑不改变原始上传名和存储键；标签采用整体替换，空数组表示清空，保存前规范化并去重。删除先设置 `deleted_at` 并解除标签，使资料立即从详情/列表隐藏，再清理原件；文件删除失败会返回错误但不会恢复可见性，后续需要孤儿文件巡检。
4. **处理（V2+）**：仅允许受支持的文件类型与任务组合；Worker 限制并发、超时、资源配额，更新持久状态；失败提供可理解但脱敏的摘要。V3 中消息包含 ID 而非文件正文，消费先核查任务状态并防重复执行，确认完成后 ACK，重试有界，最终失败进入可观测的隔离队列。
5. **缓存（V4+）**：MySQL 是持久真相源；缓存按身份隔离、设置 TTL，变更时失效，失效后可回源。敏感内容尽量不存入 Redis；限流失败策略由风险场景决定并写测试。

## 暂不定稿

- V1 的依赖、路由、4 个迁移版本、标签/名称/预览/删除接口和目录导览已落地；隔离 MySQL 和文件目录恢复演练已验证迁移、资料元数据、原件与派生产物哈希链路。文件系统与数据库仍不是同一事务，孤儿文件巡检必须持续保留。
- 当前已支持 PDF/TXT/Markdown 文本提取、PDF 登录后内联预览和 PNG/JPEG/WebP 图片缩略图；OCR、转换 Markdown 的支持矩阵仍以选定工具的能力和安全评估为准。
- 对象存储、Kubernetes、跨节点数据库/缓存高可用和全文检索只有在场景与数据证明需要时才进入落地；跨用户隔离已经是当前系统的强制权限边界。

## V2 已实现的处理闭环

V2 通过同一持久任务模型提供两类手动处理器：

1. 详情页通过 `POST /api/resources/:id/jobs` 手动创建 `extract_text` 或 `generate_thumbnail` 任务，Service 校验资料仍可见、类型允许并记录来源 SHA-256。
2. `cmd/worker` 从 `processing_jobs` 领取 `pending` 或租约过期任务；MySQL 事务使用行锁和 `SKIP LOCKED`，租约令牌防止旧 Worker 覆盖新结果。
3. `internal/processing/text.go` 将 TXT/Markdown 原文或 PDF 文本转为 UTF-8；`internal/processing/thumbnail.go` 在解码前检查图片边长和像素总量，再生成最大 640×640 的 PNG；处理失败保存固定中文摘要，不回显本地路径。
4. 结果先写入 `data/derived` 临时文件并原子移动，再在事务中写入 `derived_assets` 和成功状态；原件始终只读。
5. `derived_assets.content_text` 作为受控检索索引参与资料名称、原始名称和派生正文的关键词检索；文本和缩略图均可下载，缩略图另提供受权限保护的内联预览，不把正文拼入 JSON。

V2 当前不做 OCR、AI 摘要、自动任务和消息队列。图片缩略图不复用文本任务类型，独立记录 `generate_thumbnail` 任务和 `thumbnail` 派生产物。
