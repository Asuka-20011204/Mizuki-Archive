# ADR 0004：V2 持久任务与单进程 Worker

- 状态：已实施（首个文本处理切片）
- 日期：2026-09-29
- 范围：个人数字信息管理系统 V2

## 背景

V1 已经完成资料上传、整理、检索、预览、下载和删除。下一步需要让耗时处理可见、可重试、可追踪，但当前没有足够证据证明必须立即引入 RabbitMQ 或 Redis。为了保持目录易懂、便于学习和验证，V2 先使用 MySQL 持久化任务表和一个受控的 Go Worker；等任务语义、失败模式和负载基线稳定后，再评估 MQ。

## 决策

V2 采用“API 写任务 + MySQL 任务队列 + 单进程 Worker + MySQL 结果元数据”的单体方案：

```text
Vue 任务按钮
    │ HTTP
    ▼
Controller → Service → ProcessingJob Repository → MySQL
                                      ▲
                                      │ claim / lease
                                Go Worker
                                      │
                                      ▼
                          受控文件读取/产物写入
```

API 和 Worker 可以先运行在同一个 Go 模块的不同命令入口中：

- `cmd/server`：继续提供登录、资料和任务查询接口。
- `cmd/worker`：只负责领取任务、执行处理器、保存结果和更新状态。
- `internal/processing`：放处理器接口、状态转换、重试策略和执行上下文；不让 Controller 直接调用外部处理库。
- `internal/repository`：增加任务和派生文件的 GORM 持久化接口。

## 首个处理类型候选（已选择 V2-B，并扩展覆盖 V2-A）

默认建议选择 **文本资料提取**，但在编码前需要确认具体范围：

- V2-A：TXT/Markdown 规范化为可检索文本，并生成一份派生 `.txt` 文件。实现简单，适合先验证任务闭环，但业务难度较低。
- V2-B：PDF 文本提取并生成派生 `.txt` 文件。更贴合资料管理价值和简历表达，但需要先选定解析库并验证畸形 PDF、页数、输出质量和资源上限。
- V2-C：图片缩略图生成。视觉反馈直观，但需要处理像素上限、解码资源耗尽和图片方向等边界。

在没有确认工具、安全限制和验收数据集前，不实现 OCR、AI 摘要、自动分类或多格式转换。

## 数据模型提案

### ProcessingJob

| 字段 | 作用与约束 |
| --- | --- |
| `id` | 服务端生成的 32 位十六进制 ID。 |
| `resource_id` | 关联资料；资料被软删除后不再允许新建任务。 |
| `kind` | 处理类型，如 `extract_text`；使用白名单。 |
| `source_sha256` | 创建任务时记录原件哈希，防止资料被替换后产物错配。 |
| `status` | `pending`、`processing`、`succeeded`、`failed`。 |
| `attempts` | 已领取次数，最多 3 次；不允许无限重试。 |
| `available_at` | 任务可领取时间，用于退避。 |
| `lease_until` | Worker 租约到期时间；进程崩溃后可重新领取。 |
| `last_error` | 脱敏、可理解的失败摘要，不保存原文或堆栈中的路径。 |
| `created_at` / `started_at` / `finished_at` | 展示时间线和排查耗时。 |

同一资料、同一处理类型、同一 `source_sha256` 的未完成/成功任务默认幂等：重复点击返回已有任务，而不是重复创建。

### DerivedAsset

| 字段 | 作用与约束 |
| --- | --- |
| `id`、`job_id`、`resource_id` | 关联任务和来源资料。 |
| `kind` | 产物类型，如 `extracted_text`。 |
| `storage_key` | 服务端生成的文件键，不能使用用户输入。 |
| `mime`、`size_bytes`、`sha256` | 产物校验信息。 |
| `created_at` | 产物生成时间。 |

派生文件不能覆盖原件；写入临时文件、校验哈希后原子移动，再提交元数据。

## 状态机

```text
pending ──claim──> processing ──success──> succeeded
   ▲                    │
   │                    ├─ retryable failure ──> pending
   │                    └─ permanent/limit failure ──> failed
   │
   └──── lease expired / worker crash ────────────────┘
```

- 只有 `pending` 或租约已过期的 `processing` 任务可以被领取。
- 领取必须在数据库事务中完成：按 `available_at` 排序，使用 MySQL 8 的行锁和 `SKIP LOCKED`，更新为 `processing` 并写入 `lease_until`。
- Worker 完成前不 ACK 外部消息，因为 V2 没有外部消息；数据库状态是唯一任务真相源。
- 处理器必须检查 `source_sha256` 和资料是否仍可见；资料被删除时任务转为 `failed` 或 `cancelled`，不读取已删除原件。
- 成功写入派生文件和元数据后，任务才转为 `succeeded`；任一步失败都要清理临时文件。

## 重试与资源边界

- 默认最多 3 次尝试，退避建议为 1 分钟、5 分钟、30 分钟；具体值以测试和本地体验调整。
- 可恢复错误：临时文件锁、短暂数据库连接失败、可重试的处理器错误。
- 不可恢复错误：不支持的格式、文件损坏、超过页数/像素/输出大小限制。
- 单任务必须有执行超时、输入大小上限、输出大小上限和处理器级内存/像素边界。
- Worker 默认单并发；只有测量证明需要时才增加 Worker Pool，避免在 V2 伪造吞吐承诺。

## API 提案

- `POST /api/resources/:id/jobs`：创建或返回幂等任务；请求只包含处理类型，不上传文件正文。
- `GET /api/jobs/:id`：查询任务状态、尝试次数、时间和脱敏失败摘要。
- `GET /api/resources/:id/jobs`：查看某份资料的任务历史和成功产物。
- `GET /api/derived-assets/:id/download`：下载受权限保护的派生文件。

Controller 只校验 HTTP 输入和返回状态码；Service 负责“资料可见、类型允许、任务幂等”；Repository 负责事务、行锁和状态更新；Worker 负责调用处理器，不直接处理 Gin 请求。

## 安全与隐私

- 数据库任务表只保存 ID、类型、哈希和状态，不放原文件或完整提取文本。
- Worker 以最低权限运行，处理目录不暴露为静态资源，不允许处理器访问网络。
- 产物和临时文件使用服务端生成键；失败时删除临时文件，日志只记录任务 ID、类型、耗时和脱敏错误。
- 删除资料后不再领取其任务；已运行任务发现来源哈希或可见性不一致时停止并清理产物。
- 任务接口继续使用 V1 的会话和 Origin 保护。

## 测试与退出条件

V2 实施前先准备固定、脱敏的测试数据集和预期结果。退出条件至少包括：

- Service：支持类型校验、幂等创建、状态转换、重试上限和失败分类。
- Repository：领取竞争、租约过期、重复完成、事务回滚和软删除资料过滤。
- Worker：成功、永久失败、可重试失败、超时、进程中断后重新领取、临时文件清理。
- HTTP：创建任务、查询状态、权限、错误结构和重复请求。
- 浏览器：任务提交、处理中、成功、失败/重试和产物下载状态清晰可见。
- 实测记录：处理耗时、输入/输出大小、失败比例和单 Worker 的资源占用；不写未经测量的吞吐数字。

## 暂不引入 RabbitMQ/Redis 的理由

- RabbitMQ 解决的是跨进程投递、积压、ACK、重试和隔离队列问题；V2 先用 MySQL 任务表验证这些业务语义，避免把队列可靠性问题和处理器问题同时引入。
- Redis 适合缓存、限流或短期状态，但任务持久性仍应以 MySQL 为准；V2 没有确定的热点读或限流数据，不提前添加缓存失效复杂度。
- V3 若确有跨进程积压，再引入 outbox/发布确认、幂等消费者、有限重试和死信队列；消息只携带任务 ID，不携带原文件内容。

## 已决事项与后续问题

1. 首个处理类型已选为 `extract_text@v1`，覆盖 PDF、TXT 和 Markdown；图片缩略图另行设计。
2. 任务由用户在详情页手动触发，已实现。
3. 成功派生文本已进入资料关键词检索，使用 `LOCATE`，后续再根据数据规模评估全文索引。
4. 失败任务当前由 Worker 按最大尝试次数控制；手动重试按钮留作后续明确需求。
## 实施结果（2026-09-29）

用户确认按需处理资料，并要求详情查看、派生文件下载和关键词检索。本轮选择 `extract_text@v1`：

- 输入：PDF、TXT、Markdown；TXT/Markdown 保留 UTF-8 纯文本，PDF 使用 `github.com/ledongthuc/pdf` 提取文本。
- 触发：详情页手动触发，API 幂等复用同一来源 SHA-256 的等待中、处理中或成功任务。
- 执行：`cmd/worker` 单进程轮询 MySQL 持久任务；任务租约 5 分钟，最多 3 次领取，成功/失败状态可查询。
- 结果：派生 `.extracted.txt` 写入 `data/derived`，`derived_assets` 保存哈希、大小和检索正文；原件不覆盖。
- 查询：资料关键词搜索同时检查展示名、原始文件名和成功派生文本正文。

本轮暂不实现图片缩略图；它需要单独的图像解码、像素上限和内存耗尽防护，后续不能把图片任务伪装成文本任务。Redis、RabbitMQ、OCR 和自动触发仍保持在后续阶段。
