# ADR 0001：个人数字信息管理产品边界与分阶段技术栈

- 日期：2026-09-29
- 状态：**部分被后续决策细化**（产品、主技术栈与 MVC 分层已确认；多用户身份与归属边界由 ADR 0007 细化）

## 背景

简历中的博客/内容管理经验已覆盖 Go Web 和资源管理；新的项目需要有独立、真实的用途，而非换名重复 CRUD 或构造不可信的高并发故事。用户明确要求**个人数字信息管理**，且后端使用 Go；希望在学习 Redis 和消息队列后自然扩展，Git 提交描述使用中文，安全按正式项目对待。

## 决定

以面向多个独立用户的个人资料场景为产品边界，先交付资料收纳、整理、查找 PDF/图片/Markdown/TXT 等数字信息的基础切片；随后做可追踪的异步处理。V1 使用 Go + Gin + MySQL + 受控本地文件存储，前端 Vue 3 + TypeScript；单文件限制 50 MB。Go 后端采用 Model/Controller/Service/Repository 分层，Vue 承担 View；Repository 后续采用 GORM，见 ADR 0002。V2 用持久任务和 Worker 建立处理闭环；V3 有必要时引入 RabbitMQ；V4 在监测到热点与限流需求后引入 Redis；Docker、压测、Kubernetes 作为后续验证和可选部署。

## 理由与权衡

- Go 保持与简历主线一致；Gin/MySQL 与既有经验衔接。Vue 3/TypeScript 由用户确认；分层保持 Controller 简单、业务可测试，避免为了“标准”而制造无业务价值的空接口。
- 单体 + 独立 Worker 比拆分多个服务更容易交付和测试；新增 MQ 会带来消息一致性、重试与运维成本，只有在持久任务闭环可用后才值得引入。
- MySQL 保存持久状态，本地文件保存原件；跨资源一致性、备份与权限比选用某个框架更重要。
- 高并发和高可用是项目级工程目标，不是产品名称或未经验证的成果承诺；之后针对任务积压、热点查询、多实例和故障切换做可复现的测量和改进。

## 未决问题与复审点

单管理员身份机制以可撤销的服务端会话为初始实现；备份位置和首个处理类型待后续确认。方案变化时新增 ADR 而非悄悄覆盖历史。
